## 1. Общая цель
Добавить и отладить поддержку терминалов, подключённых через устройство КАДОПАМ‑КРК (ДКС) в эмуляторе БЭСМ‑6.

**Связанный проект:** `~/Yandex.Disk/re_dispak/re-dispak` — анализ ОС Диспак, модуль СВЯЗЬ7 (зона 0677).

см. Правило С1 в .clinerules): `~/Yandex.Disk/re_dispak/re-dispak/ai/СПРАВОЧНИКИ.md`
(индекс), `ai/справочник_<МОДУЛЬ>.md`.

## 3. Архитектура эмулятора
- Эмулятор написан на C, базируется на SIMH.
- Моделирует процессор БЭСМ‑6, память, внешние устройства (диски, ленты, АЦПУ, терминалы).
- Терминалы представлены массивом `tty_unit[27]`:
  - `[0]` — тактовый таймер;
  - `[1..24]` — последовательные линии (ТТ или ВТ‑340);
  - `[25..26]` — параллельные «Консулы».
- Каждая линия имеет флаги (`tty_unit[num].flags`), определяющие режим работы:
  - `TTY_OFFLINE_STATE`, `TTY_TELETYPE_STATE`, `TTY_VT340_STATE`, `TTY_CONSUL_STATE`;
  - `TTY_MUX_MODE` — линия работает через мультиплексор (АС);
  - `TTY_DKS_MODE` — линия работает через ДКС (КАДОПАМ‑КРК).

**Навыки:**
- `GENS_AGENTS.md` — работа с генератором системы ГЕНС и сменой конфигураций

## 4. Модель терминалов
Эмулятор **не читает** конфигурацию ОС Диспак. Всё задаётся пользователем через команды эмулятора:
- `SET ttyN [tt|vt|consul|off]` — тип линии;
- `SET ttyN [mux|dks]` — режим подключения;
- `ATTACH ttyN <порт>` — сетевое подключение;
- `ATTACH ttyN console` — локальная консоль.

Активные линии собираются в маски `tt_mask` и `vt_mask`. Для MUX и DKS эти маски не используются: обработка идёт через отдельные механизмы (`mux_*` и `dks_*`).

## 5. Поддержка ДКС (КАДОПАМ‑КРК)
### 5.1. Память КАДОПАМ
Эмулятор содержит массив `kadopam_mem[65536]` — образ 16‑разрядной памяти микро‑ЭВМ «Электроника‑60».  
Доступ к нему из БЭСМ‑6 осуществляется командами **032** (чтение) и **132** (запись).  
Обработка этих команд находится в `besm6_cpu.c`: функции `read_032()` и `write_032()`.

### 5.2. Прерывания
При работе ДКС используются прерывания ПРП (периферийный регистр прерываний):
- **ПРП5** — внимание / быстрый обмен;
- **ПРП6** — готовность приёма (медленный обмен);
- **ПРП7** — запрос ввода H‑терминала;
- **ПРП8** — готовность к передаче (быстрый обмен);
- **ПРП12** — запрос ввода S‑терминала / системный запрос.

Каждому событию соответствует константа в `besm6_cpu.c`:
- `KADOPAM_EVENT_SREQ` (ПРП12),
- `KADOPAM_EVENT_XMIT` (ПРП8),
- `KADOPAM_EVENT_ATTN` (ПРП5),
- `KADOPAM_EVENT_RECV` (ПРП6),
- `KADOPAM_EVENT_TERMREQ` (ПРП7).

Функция `kadopam_svc()` вызывается по таймеру и устанавливает биты в `PRP` и `GRP`.  
Внешнее прерывание процессора инициируется в `sim_instr()` при условии `(GRP & MGRP)` и разрешённых прерываниях в `M[PSW]`.

### 5.3. Подключение терминала через ДКС
Алгоритм (должен быть реализован в `besm6_tty.c`):

1. При новом telnet‑подключении, если линия в режиме `TTY_DKS_MODE`, вызывается `dks_register(num, line)`.
2. `dks_register`:
   - выделяет структуру `dks_term`;
   - назначает базовый адрес буфера в `kadopam_mem` (начиная с `0x2000`, шаг `0x100`);
   - записывает команду подключения в системный буфер S‑машины:
     ```c
     kadopam_mem[000154] = 1;          // команда 1 – подключение
     kadopam_mem[000155] = unit;       // логический номер терминала
     kadopam_mem[000156] = base_addr;  // адрес буфера S‑терминала
генерирует прерывание ПРП12 (KADOPAM_EVENT_SREQ).

ОС Диспак по прерыванию ПРП12 читает системный буфер, выполняет процедуру нтерм7 и подключает терминал.

4.4. Приём символа
При нажатии клавиши на telnet‑клиенте:

dks_poll() опрашивает линию, получает символ через tmxr_getc_ln().

Символ записывается в kadopam_mem[base_addr] (16‑бит).

Генерируется прерывание ПРП7 (KADOPAM_EVENT_TERMREQ).

ОС по ПРП7 читает данные из буфера S‑терминала и передаёт в МОТТ.

5. Текущее состояние и известные проблемы
Эмулятор генерирует прерывания, но ОС не реагирует (нет сообщений о чтении/записи из КАДОПАМ).

По логу видно, что внешние прерывания возникают, но в GRP часто присутствует только бит таймера, а не ПРП.

Причина, вероятно, в том, что ОС не инициализировала ДКС (модуль СВЯЗЬ7 не загружен) или маски MGRP/MPRP не установлены.

В эмуляторе уже добавлены принудительные маски в cpu_reset, но они могут быть сброшены ОС.

6. Задачи для агента
Проверить обработку команд 032/132:

Адресация должна быть 15‑битной (addr &= 077777).

Запись: извлекать 16 бит из разрядов 24–39 сумматора ((val >> 24) & 0xFFFF).

Чтение: возвращать значение, сдвинутое влево на 24, и объединять с младшими 24 битами сумматора.

Проверить dks_register:

Обязательно записывать команду подключения в kadopam_mem[000154..156].

Генерировать KADOPAM_EVENT_SREQ (ПРП12), а не XMIT.

Проверить dks_poll:

Генерировать KADOPAM_EVENT_TERMREQ (ПРП7) при поступлении символа.

Убедиться, что маски устанавливаются:

В cmd_033 при записи MPRP автоматически устанавливать бит 37 в MGRP.

В kadopam_svc для всех событий добавлять MGRP |= GRP_SLAVE; (если ещё не сделано).

Проверить сброс PRP:

Гашение PRP должно выполняться по команде УВВ 030 с правильной маской (PRP &= ACC | PRP_WIRED_BITS;), не инвертировать.

Проверить инициализацию ДКС в ОС:

Убедиться, что модуль СВЯЗЬ7 присутствует в образе диска 2053 (зона 0677) и загружается при старте.

Если модуль отсутствует, для теста можно временно эмулировать подмену векторов прерываний ПРП 5–8,12 на заглушки, которые сбрасывают соответствующий бит PRP и вызывают обработчик.
```

```
### Находка 2026-09-05 (анализ пути загрузки СВЯЗЬ7 без экстракода)
Ключевой вывод: **метка `завобм` в testdks/vnimanije.txt = `загруз` в konfus.be:870**
(в текущем тексте КОНФУСА процедура переименована; vnimanije.txt приведён
к текущему тексту — завобм→загруз, локальная завоб1 = туссв7 в konfus.be).

Автоматическая загрузка головы модуля СВЯЗЬ7 происходит БЕЗ экстракода,
штатным прерыванийным путём:

1. ПРП6 (готовность приёма) → обработчик из ОБВНП3 (векторы подменяются
   в `нстдкс`, konfus.be:903).
2. `свядкс` (konfus.be:940–985):
   - `кк 26,'0'` — чтение РКС (счётчика прерываний) через механизм Э50133
     (команда 032 к КАДОПАМ);
   - флаги готовности направлений → `рабнст`;
   - новые флаги (не в МПРП) → `или р12прп`, `пв УСТПРП` — установка
     битов 6/12 в МПРП;
   - по активному биту 6: `ГАШПРП`, `сч E46`, **`пб загруз`**.
3. `загруз` (konfus.be:870): сброс шкраб7; если E24 уже в ШГ — выход;
   иначе снятие E24 из ШКСВН, настройка ивсв7 (М33/М27), установка
   **E24 в ШГ** и запись в `ТУС-1+'31'` (Е24-СВЯЗЬ7, disp70.be:614)
   значения `аивсв7` → планировщик подкачивает ИПЗ СВЯЗЬ7.

УСЛОВИЕ входа в `загруз` без экстракода: после опроса РКС должен
остаться непогашенный флаг в бите 6 ПРП (рабнст & р6прп ≠ 0). Значит
в эмуляторе обязаны выполняться:
- бит 6 ПРП установлен (KADOPAM_EVENT_RECV/ПРП6, а не только ПРП12/ПРП7);
- РКС (032-чтение счётчика прерываний КРК) возвращает ненулевые биты
  готовности направления 0 — иначе свдкс2/свдкс3 дают 0 и уход на
  `НЕЗАВИ-Н(М7)` вместо загруз;
- в логе наблюдали `MPRP=000000` — ОС не проходила УСТПРП → РКС/флаги
  приходили нулевыми либо обработчик не запускался.

Аварийный путь: Э50 '133' с МАСДКС (konfus.be:558, из КЗК71) — авост
при неотвечающем ДКС; целевой путь — ПРП6 → ОБВНП3 → свядкс → загруз.

### Находка 2026-09-05б (уточнение адресации РКС + имитация в эмуляторе)
1. `кк 26,'0'` в `свядкс` читает слово РКС по **032-адресу 0** (регистр 0
   ```

## 7. Критерии успеха
При подключении telnet к линии с режимом DKS в логе появляются:

DKS terminal registered: unit=N, base=0xXXXX

+++ KDP: генерация прерывания ПРП12 (SREQ)

ОС Диспак отвечает на подключение (в логе появляются записи в буфер H‑машины, приглашение на терминале).

## 8. Конфигуратор системы ГЕНС

### 8.1. Общие сведения
ГЕНС — генератор системы ОС Диспак. Создаёт конфигурацию системы на основе входного файла `.b6`.
Варианты конфигураций находятся в связанном проекте: `~/Yandex.Disk/re_dispak/re-dispak/gens/`

**Форматы файлов:**
- `.b6` — входной файл конфигурации для ГЕНС (формат БЭСМ-6)
- Файлы `1`–`9` — примеры конфигураций с входной информацией и результатом работы ГЕНС

### 8.2. Структура файла конфигурации (.b6)

**Заголовок файла:**
```
ШИФР <код>‾ОЗУ <объём>‾ВХО <количество_входов>‾ВРЕ <время>‾РОС <режим>‾Е
B63
K 07 010 0074 00 050 0131      # Команды загрузки
K 07 26 00065 00 074 0000
...
C 0010 0100 0030 0752          # Константы
...
B100A1                        # Начало описания конфигурации
```

**Директивы конфигурации (после B100A1):**

| Директива | Описание | Пример |
|-----------|----------|--------|
| `МЛЗАГ` | Магнитная лента загрузчика | `МЛЗАГ 2053-560^` |

### 8.3. Конфигурация терминалов

**Ключевые директивы для терминалов:**

| Директива | Описание | Пример |
|-----------|----------|--------|
| `ТТ` | Номер телетайпа (главный терминал) | `ТТ 1^` |
| `ТЕРМ` | Подключённые терминалы | `ТЕРМ VT:1-10^` |
| `ТЕРМ` | Терминалы через АС (МУКС) | `ТЕРМ АС,ТТ:11-16^` |
| `ТЕРМ` | Терминалы через АС (VT) | `ТЕРМ АС,VT:3-47^` |
| `ЕСТЕР` | Дополнительные терминалы | `ЕСТЕР 1-35^` |
| `ЧАСЫ` | Тип часов | `ЧАСЫ ИПМ^` |

**Форматы описания терминалов:**

1. **Локальные терминалы (VT/ТТ):**
   - `ТЕРМ VT:1-10` — терминалы ВТ-340, линии 1-10
   - `ТЕРМ TT:1-16` — телетайпы, линии 1-16

2. **Терминалы через АС (МУКС — мультиплексор):**
   - `ТЕРМ АС,ТТ:11-16` — телетайпы через АС, линии 11-16
   - `ТЕРМ АС,VT:3-47` — ВТ-340 через АС, линии 3-47

3. **Терминалы через ДКС (КАДОПАМ-КРК):**
   > В конфигурациях ГЕНС ДКС-терминалы обычно не указываются явно.
   > Для ДКС требуется наличие модуля СВЯЗЬ7 (зона 0677).
   > Настройка ДКС в эмуляторе выполняется командами:
   ```
   SET ttyN vt          # тип терминала
   SET ttyN dks         # режим ДКС
   ATTACH ttyN <порт>   # подключение
   ```

### 8.5. Секция "ИНФОРМАЦИЯ К ГЕНСУ"

После описания конфигурации идёт секция с 16-ричными данными (адреса 72000-72030):
```
ИНФОРМАЦИЯ К ГЕНСУ

72000
 0000056000004005    # Конфигурационное слово 0

72010

```

Эти данные формируются ГЕНС на основе входной конфигурации.

### 8.6. Связь конфигурации ГЕНС с эмулятором

**Важно:** Эмулятор НЕ читает файлы конфигурации ГЕНС.

Соответствие между конфигурацией ГЕНС и настройками эмулятора:

| ГЕНС | Эмулятор (команда) |
|------|-------------------|
| `ТТ 1` | `SET tty1 tt` |
| `ТЕРМ VT:1-10` | `SET ttyN vt` для N=1..10 |
| `ТЕРМ АС,ТТ:11-16` | `SET ttyN tt`, `SET ttyN mux` для N=11..16 |
| ДКС (СВЯЗЬ7) | `SET ttyN dks` для нужных линий |

**Пример настройки эмулятора под конфигурацию:**
```ini
# Конфигурация терминалов для gens_rab.b6
# VT:1-30
SET tty1 vt
ATTACH tty1 4001
...
SET tty30 vt
ATTACH tty30 4030

# АС,ТТ:3-10
SET tty3 tt
SET tty3 mux
...
```

## 9. Оптимизация работы Cline

### 9.1. Правила экономии токенов

Проблема: в сессии отладки ДКС было потеряно ~20,000 токенов (30%) из-за:
- Таймаутов при многократной сборке
- Повторного чтения одних файлов
- Дублирования grep-запросов
- Лишних диагностических команд

#### Правило 1: Пакетные операции

**Всегда группировать независимые операции в один вызов.**

```
Плохо:
  read_files: [besm6_cpu.c]
  read_files: [besm6_tty.c]
  read_files: [dispak.ini]

Хорошо:
  read_files: [besm6_cpu.c, besm6_tty.c, dispak.ini]
```

Экономия: ~3,000 токенов на задачу.

#### Правило 2: Фоновые команды

**Долгие команды (make, gcc, npm test) всегда в фоне.**

```
Плохо:
  run_commands: ["make"]  # Таймаут!

Хорошо:
  run_commands: ["make > /tmp/build.log 2>&1 &"]
  run_commands: ["sleep 3; tail -20 /tmp/build.log"]
```

Экономия: ~5,000 токенов на таймаут.

#### Правило 3: Кэширование поиска

**Сохранять результаты grep во временные файлы.**

```
Плохо:
  grep -rn "TMXR_VALID" *.c  # Первый раз
  grep -rn "TMXR_VALID" *.c  # Повтор!

Хорошо:
  grep -rn "TMXR_VALID" *.c > /tmp/search_tmxr.txt
  cat /tmp/search_tmxr.txt  # При необходимости
```

Экономия: ~1,500 токенов на повтор.

#### Правило 4: Ограничение вывода

**Использовать head/tail для больших файлов.**

```
Плохо:
  cat debug.txt  # Весь файл

Хорошо:
  tail -50 debug.txt
```

Экономия: ~500 токенов на вызов.

#### Правило 5: Убрать декорации

**Не использовать echo для разделителей.**

```
Плохо:
  echo "=== Начало секции ==="
  echo "--- Конец ---"

Хорошо:
  # Просто выполнить команды без декораций
```

Экономия: ~2,000 токенов на сессию.

Карты кода (`.cline/maps/*.map`) заменяют полное чтение C-файлов структурной
сводкой (~2k токенов вместо ~27k). Сжатие применяется **автоматически** —
правила M1–M6 в `.clinerules` без триггеров:

| Шаг | Когда | Действие | Правило |
|-----|-------|----------|---------|
| 1 | Старт сессии | `./scripts/gen_code_map.sh --check` | M5 |
| 2 | Обращение к LARGE_FILES | Читать `.map`, НЕ полный файл | M1/M6 |
| 3 | Поиск символа | Найти в `.map` → `read_files` с range | M2 |
| 4 | После правки | `--check <file>` для актуализации карты | M6.3 |

Карты генерируются awk-парсером `scripts/gen_map.awk` (вызывается через
`scripts/gen_code_map.sh`). Парсер извлекает: функции (с диапазонами строк),
глобальные переменные, `#define`, `typedef`/`struct` — автоматически из исходника.

**LARGE_FILES** (файлы с картами):
- `besm6_cpu.c` (2105 строк → ~2k токенов, сжатие 13×)
- `besm6_tty.c` (1700 строк → ~1.8k токенов, сжатие 12×)
- `besm6_mmu.c`, `besm6_disk.c`, `besm6_defs.h`

Подробности: `.cline/skills/code-map.md`.

### 9.8. Жёсткие триггеры исполнения (введены 2026-09-06)

Навыки и правила применяются не по «доброй воле», а как обязательные шаги.
Основание: анализ сессий 2026-09-05 показал 40 чтений LARGE_FILES напрямую
против 1 чтения карты — с этого момента такие чтения считаются ошибкой.

**Триггер 1 — карта перед LARGE_FILES (усиление M1/M6):**
Перед каждым read_files/run_commands, обращающимся к `besm6_cpu.c`,
`besm6_tty.c`, `besm6_mmu.c`, `besm6_disk.c`, `besm6_defs.h`:
1. СНАЧАЛА `read_files: [.cline/maps/<файл>.map]`;
2. Только затем целевое чтение диапазона (start_line/end_line после карты);
3. Если карта устарела — `./scripts/gen_code_map.sh --check <файл>`.

**Триггер 2 — старт сессии (усиление M5):**
Первое действие первой задачи сессии над кодом БЭСМ-6:
`./scripts/gen_code_map.sh --check` — ДО ответа пользователю, без запроса
разрешения (~100 токенов).

**Триггер 3 — вызов навыков инструментом `skills`:**
Если задача совпадает с доменом навыка (ДКС/трассы → dispak-tracer;
модули ОС → dispak-modules; команды эмулятора → dispak-commands;
большой файл → code-map; сложная задача → small-portions; структура
БЭСМ-6 → bemsh-analyzer; экономия токенов → token-saver) — навык
ВЫЗЫВАЕТСЯ инструментом `skills`, а не упоминается текстом.

### 10.1а. Тесты КАДОПАМ (test_k71.txt, test_sis_k71.txt)

Тест **test_k71.txt** требует аппаратной имитации
перехватчика прерываний ДКС. В текущей эмуляции это
не реализовано — модель упрощённая (прямая
запись/чтение kadopam_mem). Полная эмуляция
требует моделирования регистров РСС/РБП/РПР
на стороне Э-60 (из документа НИТИ, 2005/2024).

Тест **test_sis_k71.txt** проверяет ОЗУ ДКС
через команды 132/032 (МАДЛЕН Z13/Z03).
Эти команды нестандартные — придуманы для
расширения КАДОПАМ (К-71). Диапазон ОЗУ ДКС:
10–67777₈ (уточняет «00000–77777» в rukdks.be).

#### Соответствие БЕМШ↔МАДЛЕН↔БЭСМ-6 (команды КАДОПАМ)

| БЕМШ             | МАДЛЕН            | БЭСМ-6       | Назначение                          |
|------------------|-------------------|--------------|-------------------------------------|
| `кк 26,00000`    | `Z03,0` / `,032,` | `032,000000` | Чтение из адреса 0 ДКС (РКС)       |
| `кк 26,70000`    | `Z13,20000B` / `,132,` | `132,00000`  | Запись в адрес 0 ДКС (РКС)         |
| `кк 26,00XXX`    | `Z03,XXXXX` / `,032,` | `032,XXXXX`  | Чтение из kadopam_mem[XXXXX]        |
| `кк 26,70XXX`    | `Z13,XXXXX` / `,132,` | `132,XXXXX`  | Запись в kadopam_mem[XXXXX]         |

**Ключевая привязка:**
- `кк 26` в БЕМШ — короткая команда КАДОПАМ (тип устройства 26); `дк` — длинная команда
- Префикс `0`/`7` в БЕМШ-адресе определяет направление: `0xxxx` → чтение (032₈), `7xxxx` → запись (132₈)
- `Z13` / `,132,` в МАДЛЕН = команда 132₈ (write to kadopam)
- `Z03` / `,032,` в МАДЛЕН = команда 032₈ (read from kadopam)
- Адрес `70000₈` (БЕМШ) = `20000₈` (МАДЛЕН) = адрес 0 ДКС (РКС)

## 13. Дробление сложных задач (анти-таймаут)

Ошибка провайдера «The model did not respond in time» возникает при длинном
«забеге» модели или большом контексте. Алгоритм дробления:

| Шаг | Действие | Запрет |
|-----|----------|--------|
| 1 | Анализ задачи → краткий вывод, **без правок** | Не читать полные файлы, только карты `.cline/maps/` |
| 2 | План из N шагов (каждый ≤ 4 вызовов) | Не объединять несколько правок в шаг |
| 3 | Выполнение шага → остановка → diff | Не «забегать» вперёд |
| 4 | После вехи — `/newtask` (новая задача с summary) | Не тащить старый контекст дальше |

**Критерии разбивки запроса:**
- Ожидается > 3-4 инструментальных вызовов → разбить на 2-3 запроса;
- Правка > 100 строк → частями («внеси только часть 1, остановись»);
- Контекст сессии > 60k токенов → `/newtask`;
- Логи/состояние эмулятора → командой (`tail -50 debug.txt`), не вставкой в промпт.

**Практическое правило:** короткий запрос → быстрый первый токен → нет
таймаута; обрыва с потерей работы тоже нет.

**При возникновении таймаута (правило T7):** НЕ повторять запрос целиком —
разрезать на 2-3 порции (T1/T2), при большом контексте сначала `/newtask`;
чистый ретрай — только если исходный запрос был коротким и лёгким.

## 14. Журналирование по подсистемам (per-subsystem logging)

### 14.1. Общие сведения

Вместо монолитного файла `debug.txt` эмулятор записывает сообщения
отладки в отдельные файлы по подсистемам. Это позволяет:
- быстро находить нужные сообщения (DKS, CPU, MMU и др.)
- не раздувать единый файл (ограничение размера + ротация)
- агрегировать все ошибки в один файл `errors.log`

### 14.2. Файлы подсистем

| Подсистема | Имя файла       | Описание                          |
|-----------|----------------|-----------------------------------|
| `SYS`     | `debug_sys.log` | Системные события                  |
| `CPU`     | `debug_cpu.log` | Команды процессора, регистры       |
| `DKS`     | `debug_dks.log` | КАДОПАМ, терминалы, ПРП, прерывания|
| `MMU`     | `debug_mmu.log` | Модуль управления памятью          |
| `DISK`    | `debug_disk.log`| Операции с дисками                 |
| `VU`      | `debug_vu.log`  | Перфокарточное устройство          |
| `PRN`     | `debug_prn.log` | Принтер АЦПУ                       |
| `PUNCH`   | `debug_punch.log`| Перфолента (ФС1500)               |
| `PL`      | `debug_pl.log`  | ПЛ-80 (перфокарточный)             |
| `TTY`     | `debug_tty.log` | Терминалы (VT, TT, CONSUL, MUX)    |
| `ERRORS`  | `errors.log`    | Собранные ошибки всех подсистем    |

Файлы создаются в каталоге `logs/` (по умолчанию) или в каталоге,
указанном через конфигурацию.

### 14.3. Конфигурация в .ini-файле

В файл `dispak.ini` (или другой .ini-файл эмулятора) добавляются
параметры для настройки журналирования:

**Параметры для CPU-устройства:**

```ini
; === Настройка пер-subsystemного журналирования ===

; Включение/отключение журналирования (по умолчанию: ON)
; set cpu log=off    ; отключить (log файлы НЕ создаются)
; set cpu log=on     ; включить (log файлы в logs/debug_*.log)

; Каталог для файлов подсистемных логов (по умолчанию: logs/)
; Если не указан, файлы создаются в текущем каталоге
; set cpu log-dir=logs

; Максимальный размер каждого файла подсистемы (в МБ)
; При превышении файла он автоматически сжимается (ротация)
; По умолчанию: 10 МБ. 0 = без ограничения
; set cpu log-max=10
```

**Пример минимальной конфигурации (по умолчанию — `logs/`, 10 МБ, включено):**

```ini
; Журналирование устанавливается автоматически
; файлы создаются в logs/debug_*.log
; без каких-либо дополнительных строк в .ini
```

**Пример расширенной конфигурации:**

```ini
; Включить/отключить журналирование
set cpu log=on

; Каталог для логов
set cpu log-dir=/tmp/besm6_logs

; Максимальный размер файла (в МБ)
set cpu log-max=50
```

**Порядок выполнения в .ini файле:**

1. `set cpu log=on` (или `off`) — включает/отключает файловое журналирование
2. `set cpu log-dir=...` — задаёт каталог (после cpu_reset не влияет на уже открытые файлы)
3. `set cpu log-max=...` — задаёт максимальный размер файла (MB)

> **Важно:** `set cpu log=off` в .ini файле отключает журнал на уровне пер-подсистемных файлов; `debug.txt` продолжает работать независимо.

### 14.4. Порядок инициализации

1. При загрузке эмулятора и вызове `cpu_reset()` выполняется
   `besm6_log_init()`, который:
   - проверяет, инициализировано ли уже журналирование (`b6_log_is_init()`)
   - если нет, вызывает `b6_log_init()` с параметрами из конфигурации
   - создаёт каталог `logs/` (если не существует)
   - открывает 11 файлов подсистем + `errors.log`
   - устанавливает максимальный размер файла для ротации

2. При первом вызове `besm6_debug_sub()` (или макроса `BESM6_*_DEBUG`)
   - сообщение записывается в файл подсистемы (формат: `[уровень] сообщение`)
   - одновременно записывается в `sim_deb` (backward compatibility с
     существующим `debug.txt`)
   - если уровень == `B6_LOG_ERROR`, сообщение также попадает в `errors.log`

### 14.5. Уровни логирования

| Уровень    | Назначение                             | Манипуляция                  |
|-----------|----------------------------------------|-----------------------------|
| `ERROR`   | Ошибки (все ошибки пишутся в errors.log) | `b6_log_error()` / `BESM6_*_ERROR()` |
| `WARN`    | Предупреждения                           | `b6_log()` с `B6_LOG_WARN`  |
| `INFO`    | Информационные сообщения                | `b6_log()` с `B6_LOG_INFO`  |
| `DEBUG`   | Отладочные сообщения (основной уровень) | `b6_log()` с `B6_LOG_DEBUG` |
| `TRACE`   | Детальная трассировка                    | `b6_log()` с `B6_LOG_TRACE` |

Фильтрация по уровням пока не реализована — все сообщения пишутся в файлы.

### 14.6. Ротация файлов

При превышении размера файла (по умолчанию 10 МБ, настраивается через
`set cpu log-max=N`):
- файл сжимается до нуля (`ftruncate()`)
- записывается маркер `[ROTATED at N bytes]`
- запись продолжается с начала файла

Ротация происходит автоматически при каждой записи, если файл превышен.

### 14.7. Примеры использования

**Просмотр логов ДКС (терминалы, ПРП):**
```bash
tail -f logs/debug_dks.log
```

**Просмотр всех ошибок:**
```bash
cat logs/errors.log
```

**Поиск событий регистрации терминалов:**
```bash
grep 'terminal.*registered' logs/debug_dks.log
```

**Просмотр disrupt.txt (backward compatibility):**
```bash
tail -f debug.txt
```

**Очистка логов перед прогоном:**
```bash
rm -rf logs/
```

### 14.8. Код для добавления нового вызова логирования

Для добавления нового сообщения в коде эмулятора:

```c
/* Через макрос (рекомендуется) */
BESM6_DKS_DEBUG(">>> DKS: terminal %d registered", num);
BESM6_CPU_ERROR("UHV %o: address %o", addr);

/* Через функцию (для찹 elaborated логирования) */
besm6_debug_sub(B6_LOG_DKS, ">>> KDP: PRP=%06o", PRP);

/* Для ошибок (попадает также в errors.log) */
besm6_debug_sub(B6_LOG_DKS, ">>> DKS: out of buffer space");
```

### 14.9. Известные ограничения

- Фильтрация по уровням пока не реализована (все сообщения пишутся).
- Ротация происходит только при записи (нет периодического вызова).
- Не поддерживается динамическое изменение максимального размера.
- При запуске эмулятора файлы подсистем открываются один раз и не
  закрываются до завершения работы (кроме `b6_log_close()`).
